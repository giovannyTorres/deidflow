# Privacy boundaries

The public/synthetic evaluation path and the private Gmail/annotation path have different trust boundaries. All development checks in Codex use authored synthetic transports, fictional metadata and synthetic originals. A passing test does not establish that real Gmail authorization, real personal-document processing or real accuracy has been validated. The assistant must never launch real private inventory, review, annotation or processing, and must never inspect their credentials, inputs, annotation files or original-text exports.

## Operational isolation, not an OS sandbox

Real private commands require an explicit `--external-terminal-ack` and fail before loading configuration when known Codex environment markers are present. Private paths must be absolute, outside Git repositories and outside any directory named `Codex` or `.codex` (case-insensitive); symlinked paths are rejected. Windows private outputs use a protected current-user DACL; POSIX files/directories use `0600`/`0700`. Raw originals are never written into the checkout, tests, benchmark artifacts or logs.

A separate terminal under the **same OS account is not hard isolation from Codex**, other processes under that account, administrators, disk backup tools or malware. The marker guard is an accidental-use guard; arbitrary code can bypass it. Close Codex before a run, or use a dedicated OS account/VM with private credentials/files inaccessible to the Codex account when a stronger boundary is required. Encryption at rest, swap, crash dumps, backups and browser extensions are controlled by the user's operating environment. This library does not attest OS or network isolation.

## Identity and work-material gates

OAuth uses the user's deliberately supplied Google desktop client and read-only token files. There is no credential discovery, browser-cookie reuse or connector access. The fixed Gmail transport has only GET endpoints and the exact `gmail.readonly` scope; it cannot perform mail changes. The actual account profile must match the configured personal `gmail.com`/`googlemail.com` address before messages are listed. Non-Gmail domains and workspace/corporate identities are rejected; identity selection remains the user's local responsibility.

An exact personal sender list plus conservative domain/subject exclusions reduces accidental intake. BBVA/work exclusions are enabled even when a user supplies an empty denylist. A personal sender may forward work material, and an employer document can lack recognizable metadata. Consequently, the runner additionally requires a separate per-attachment personal-provenance attestation in the localhost review UI. Unreviewed and uncertain attachments are skipped without downloading bytes. An approval is user judgment and can be wrong; metadata heuristics and human attestation cannot guarantee that every corporate document is excluded. Do not approve material whose provenance or processing authorization is uncertain.

HMAC approval references include account, Gmail message/attachment identifiers, extension and declared size. The private key and decision manifest stay outside the checkout. These references support local review decisions and are not emitted in aggregate reports. A modified or differently identified attachment needs another approval. Gmail message immutability and trusted local configuration are assumptions; this is not a cryptographic document-provenance system.

## Data processing and output controls

Before attachment download, MIME, extension, date, count and declared-size filters apply. Actual response bytes and cumulative download budgets are bounded. Only individually approved attachments are retrieved. Inputs/outputs live in a new protected temporary child directory with opaque filenames; content hashes are used in memory for exact deduplication. Cleanup deletes only an owned, validated child and its files. Persistent credentials, approvals, annotation sources and annotation datasets are outside that cleanup scope. A hard crash can leave an owned private directory; review it locally rather than asking the assistant to inspect it.

Private runtime logging/stdout/stderr are suppressed around authentication and document processing. Exceptions reaching the CLI become fixed codes. Report dictionaries use a strict field/value allowlist and never include arbitrary strings or per-document metadata. Small-cohort/cell suppression and rounding reduce disclosure but provide no formal differential privacy or guarantee against singling out, repeated-query inference or external auxiliary knowledge. Only schema-validated aggregates should ever be considered for sharing; sharing is a separate user action and is not performed by the runner.

The processing engine uses the configured local OCR, local NER and format adapters. Custom model packages, executables or adapter code are trusted local code and must be reviewed before use. `--local-only` describes the built-in document processing path, not an OS firewall rule against arbitrary third-party packages. Gmail/OAuth retrieval necessarily contacts Google. The runner has no publication, telemetry, cloud inference, Git push or upload feature. De-identification status and verification are evidence about processing; they do not establish anonymous, lawful or universally safe documents.

## Browser review and annotation

The review servers bind to IPv4 `127.0.0.1` only, use fresh unprinted bearer tokens and CSRF headers, reject other Host/Origin values, provide no CORS permission, deny frames/external resources with CSP, and disable HTTP access logs. The local URL is briefly saved in a protected private file for the user; the token is removed from browser history state after page load. A compromised browser, extension or same-user process can still read displayed originals. Use a trusted browser locally, outside a model-controlled browser session.

Metadata review displays identifying metadata only after an explicit CLI display-consent flag. Annotation displays original text and rasterized pages only after a separate original-display consent. There is no upload API, raw-PDF byte route or cloud synchronization. Arbitrary local paths cannot be supplied to an HTTP request; configured source files are reached through private opaque IDs. The UI uses text/value rendering for original strings, never source HTML injection.

Annotations store validated finite geometry, fragment-local Unicode ranges, entity types, review states and grouping by default. Original excerpts and typed OCR corrections require launch consent plus a per-save opt-in. Original-text JSONL training export requires another explicit command-line consent and an outside-repository destination; it is private data and must not be opened by Codex. False positives are omitted from positive training spans; box-to-text mapping and OCR correction application are not inferred. Source mutation invalidates annotations. No private export is automatically trained, published or mixed into public synthetic gold data.
